# Operating your own installation

This runbook describes the implemented backend. This portfolio project supplies no deployed service or provider credentials. Configure your own operator identity, support contact, consent/commerce policies, accounts, backups and alerts before real use.

Member sign-in uses Supabase email codes. Authentication SMTP is required even if optional practice email is disabled. Keep delivery and payments disabled until their separate checks pass.

## Environments and secrets

Keep local preview, isolated integration/staging, and production separate. The preview is the default and does not need secrets. `NEXT_PUBLIC_APP_MODE=live` is a build-time choice for both apps, not a provider activation switch. Email, phone verification, SMS delivery, and payments each have a separate `ENABLE_*` flag; keep them false until the corresponding configuration and controlled checks are complete.

Use the app `.env.example` files as the inventory. Next.js loads its own app's `.env.local`; root Node scripts do **not** automatically load those files. For root scripts, inject variables through a secret manager/process environment, or use Node's explicit `--env-file` option against the intended ignored local file. Never add production secrets to source, build logs, screenshots, browser configuration, CLI arguments, or issue descriptions.

| Group               | Settings and responsibility                                                                                                                                                                                                                                     |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Canonical origins   | `NEXT_PUBLIC_SITE_URL` for public website; `NEXT_PUBLIC_DASHBOARD_URL` and `APP_ORIGIN` for the same member origin. Use approved HTTPS origins in deployment, without paths, queries, credentials, or fragments.                                                |
| Identity/database   | `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, server-only `SUPABASE_SERVICE_ROLE_KEY`, `DATABASE_URL`, optional `DATABASE_CA_CERT`. Auth and database must refer to the same intended project.                                                                    |
| Independent secrets | `RATE_LIMIT_SECRET`, `DESTINATION_HASH_SECRET`, `UNSUBSCRIBE_SIGNING_SECRET`, `CRON_SECRET`, `MONITORING_SECRET`; independently generated high-entropy values of at least 32 characters. The monitoring token must differ from the mutation-capable cron token. |
| Owner information   | `OPERATOR_NAME`, `OPERATOR_MAILING_ADDRESS`; actual approved values, never placeholders. Support is configured in source and is not a verified sending domain.                                                                                                  |
| Providers           | Resend, Twilio, and Stripe credentials/flags in [provider setup](provider-setup.md). `SMS_SEGMENT_PRICE_CAD_CENTS` is the approved retail rate per segment. `COMMERCE_POLICY_APPROVED=true` records an actual decision, not a way around missing policy.        |
| Edge trust          | Configure `TRUSTED_CLIENT_IP_HEADER` only when the selected edge overwrites that header and strips client-provided values. Otherwise leave it unset; global/per-destination throttles still apply.                                                              |

The server uses verified TLS for remote PostgreSQL. Do not bypass certificate validation; supply the provider CA when needed. The connection pool defaults to five connections per process, so account for all application instances in the database connection budget. Review the chosen pooler's transaction/role behavior against this app's `SET LOCAL ROLE` and claims setup in staging.

Back up secrets securely alongside the recovery plan. Rotating `DESTINATION_HASH_SECRET` without a migration breaks matching existing contacts/suppressions; rotating `UNSUBSCRIBE_SIGNING_SECRET` invalidates previously mailed links. Tokens currently expire after 180 days, and multi-key rotation is not implemented. Plan a compatible rotation before changing those keys. Credential compromise still requires prompt containment and a documented recovery decision.

## Host startup

After an authorized deployment target is configured, run each built app as a separate service with `pnpm --filter @jesus-in-practice/website start:host` and `pnpm --filter @jesus-in-practice/dashboard start:host`. The host supplies `PORT`; `start:host` listens on `0.0.0.0`, unlike the loopback-only local `start` commands. Configure canonical external origins independently of the internal port and ensure TLS terminates correctly. Build with the intended public variables and provide each app its required server settings. These commands do not provision a host, publish DNS, or authorize a deployment.

## Database setup and migrations

Use an isolated authorized Supabase database/project, or an existing local Supabase environment. Migrations expect Supabase's `auth.users`, `authenticated`, `anon`, `service_role`, and claims helpers. The repository does not provision Supabase or include a complete local Supabase CLI configuration. Embedded PostgreSQL tests create their own fixtures; they are not a deployable auth service.

1. Confirm the resolved target project/host and database identity without printing credentials. Review every new file in `database/migrations`; do not edit an already-applied migration.
2. For an existing database, take an encrypted backup using the provider's supported method, record the recovery point, and verify restoration to an isolated environment. Include account/auth data and application data required for a consistent restore, plus the matching secrets and release configuration. A backup file alone is not restore evidence.
3. Use a migration credential allowed to create schema, policies, grants, triggers, and required tables. Keep application credentials server-only and restrict them to the capabilities the runtime needs. Keep the private `app` schema out of the exposed Supabase Data API schemas.
4. After supplying `DATABASE_URL` and any CA setting to the process, run from the root:

   ```powershell
   npx.cmd --yes pnpm@10.26.0 db:migrate --apply
   ```

   For an already-reviewed local ignored environment file, an explicit alternative is:

   ```powershell
   npx.cmd --yes pnpm@10.26.0 exec node --env-file=apps/dashboard/.env.local packages/backend/scripts/migrate.mjs --apply
   ```

5. The runner obtains an advisory lock, applies files in name order, and records each file's SHA-256 in `app.schema_migrations`. Each migration and its checksum are committed atomically. A changed previously-applied checksum stops the run. Omitting `--apply` makes no changes and exits with instructions; it is not a SQL dry-run validator.
6. Run `pnpm db:check` with the same intended database/CA settings. It performs read-only queries to verify connection and role switching, RLS-enabled app tables, required migration columns/tables, and no profile/wallet visibility for a synthetic account ID. It creates no users, records, or schema and logs no credentials or row data. This is a smoke check, not proof of all policies, write permissions, concurrency, provider behavior, or complete migration correctness. Then verify the deployed schema, RLS/grants, two-account isolation, financial invariants, and export/deletion behavior with isolated staging data. Preserve the migration record and tested application revision. Use a new corrective migration for fixes; do not erase migration history or restore over a live database casually.

Application rollback and database rollback are different. Prefer backward-compatible migrations and a previous compatible application artifact. A database restore can lose post-backup payments, consent withdrawals, and provider events; suspend processing, reconcile that gap, and obtain authorization for the actual data operation before restoring production.

## Authentication and email setup

Supabase Auth sends login mail independently from practice reminders. Configure the approved member origin as its Site URL and restrict redirect allowlists to intended environments. The implemented UI submits a numeric OTP to `/api/auth/verify`; there is no app magic-link callback route. Configure the Magic Link/OTP template to display `{{ .Token }}` and review the new-user confirmation template too. Exercise both a new and existing account, incorrect/expired codes, resend throttling, sign-out, and an expired session. Do not leave a template that sends only a link the UI does not consume. [Supabase email templates](https://supabase.com/docs/guides/auth/auth-email-templates)

The prepared [Heritage authentication email](../deployment/supabase/README.md) covers both new and returning members. Install it in both relevant Supabase templates after custom SMTP is verified; the dashboard observed during setup requires custom SMTP before editing templates. Local rendering checks do not prove provider installation or inbox delivery.

Set up custom SMTP with a verified sender for production authentication. Supabase's default SMTP is restricted and is not intended for production; configure the provider, rate limits, sender reputation, and failure monitoring separately from Resend practice email. An API `sent:true` is intentionally generic and is not delivery proof. [Supabase custom SMTP](https://supabase.com/docs/guides/auth/auth-smtp)

Supply the same approved operator name and mailing address to both apps. Public privacy, terms, and support pages render that identity, and the member app shows it beside channel opt-in. Before granting SMS consent, the member sees the configured CAD price per segment. The grant submits its displayed wording/rate version; `409 CONSENT_CHANGED` prompts a refresh and another explicit choice if the version changed. Stored SMS consent is bound to that rate and is checked again during planning and submission; changing the price or wording requires renewed consent. Withdrawal remains possible without a version.

Configure Resend practice sending with a verified domain and the actual DNS records supplied by that provider. Configure Twilio Lookup/Verify plus an approved Canadian-capable toll-free SMS sender/Messaging Service with Advanced Opt-Out and Smart Encoding disabled. This app assumes toll-free SMS segmentation, not RCS/MMS. Use the detailed [provider setup guide](provider-setup.md), including its official documentation links; no sender purchase or external account connection is implied.

## Callback registration

Prefix these paths with the **canonical approved `APP_ORIGIN`**. Keep staging and production endpoint secrets separate. Do not construct callback URLs from forwarded request headers. Receive raw signed bodies; do not place a login wall or rewrite layer in front of callbacks. Verify the actual endpoint behavior before enabling outbound work.

| Provider       | URL and events                                                                                                                                                                                                                                                                                                             |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Stripe         | `/api/webhooks/stripe`: `checkout.session.completed`, `checkout.session.async_payment_succeeded`, `checkout.session.expired`, `checkout.session.async_payment_failed`, `charge.refunded`, `refund.created`, `refund.updated`, `refund.failed`, `charge.dispute.created`, `charge.dispute.updated`, `charge.dispute.closed` |
| Resend         | `/api/webhooks/resend`: `email.sent`, `email.delivered`, `email.bounced`, `email.complained`, `email.suppressed`, `email.failed`                                                                                                                                                                                           |
| Twilio inbound | `/api/webhooks/twilio/inbound`; Advanced Opt-Out STOP/START notifications, with valid account/signature                                                                                                                                                                                                                    |
| Twilio status  | `/api/webhooks/twilio/status?deliveryId=<opaque-id>` is supplied per send; preserve the query in signature verification                                                                                                                                                                                                    |

For signed Resend bounce, complaint, or suppression events, the handler validates recipient addresses and records destination-hash suppression even after the original account/delivery has been deleted. Keep the destination-hash key stable so late callbacks and future registrations match existing suppression.

The eleven listed Stripe event types match the current handler. Refund events reconcile matching durable refund requests; unmatched refunds and disputes restrict the associated wallet for review. A dispute-closed callback records evidence, not permission to unfreeze blindly. Keep refund and dispute updates subscribed after funding is enabled. Follow [financial operations](financial-operations.md) and the [operator guide](operator-guide.md) for review, provider reconciliation and recent-MFA admin actions; no direct ledger editing or automated dispute-defense submission is provided.

Callback receipts are durable and deduplicated. A receipt still marked `received` has not completed processing; inspect failures rather than marking it processed manually. Payment/session ownership, amounts, currency, mode, and signatures must match even for a correctly signed event. Configure provider retry/alert behavior and verify duplicate and out-of-order events using controlled fixtures/sandboxes.

## Scheduler and delivery recovery

The host must support a scheduled **POST once per minute** to `APP_ORIGIN/api/jobs/deliver` and a staggered POST to `/api/jobs/maintenance`, with `Authorization: Bearer <CRON_SECRET>`. The provided `pnpm ops:scheduler` process performs both calls; it has not been installed on a host. Store the secret in protected process settings, not URLs or logs. The routes request a 60-second execution limit; confirm the chosen host honors enough runtime and supports the database connection model. See [production operations](production-operations.md).

The worker uses a 90-second global lease, a persisted planning cursor, and delivery claim leases. Concurrent triggers can return `{busy:true}`. Planning processes profiles in batches of 50 and yields after its time budget. Sending claims batches of up to five deliveries while its runtime budget remains, with pacing between submissions. Current protection limits are three messages per channel/member/local day, 100 send attempts per channel per 86,400-second quota window, and at most ten segments for one SMS. These are starter capacity controls, not a delivery SLA; review queue lag and provider costs before increasing them. A separate monthly spend alert/budget is an operational requirement, not currently an application quota.

Schedules cover the current minute and previous four minutes, never times before the last relevant schedule/preference update. Missing DST local times are skipped; a repeated time shares an occurrence key. Surprise windows use one deterministic time within that day's window and one occurrence identity per member/local date/channel, independent of revisions. Editing a window cannot create another window occurrence that day; fixed-time occurrences and the overall channel daily cap retain their separate semantics. Queued messages expire ten minutes after the occurrence; an outage longer than catch-up is not fully replayed. Do not promise historical completeness or delayed catch-up delivery.

The queue freezes content/destination/consent/rate versions. Before sending, it rechecks consent and suppression, source/preferences, account deletion/pause, the selected channel, current rate, available credit, the daily cap, and current permission/publication of the exact imported content version. Withdrawal, rights revocation/expiry, or disabling imported content invalidates affected queued work; the worker does not silently substitute another lesson. Disable the relevant `ENABLE_*_DELIVERY` flag and stop delivery scheduling during a sending incident; still accept valid callbacks and withdrawals so in-flight outcomes and opt-outs can be recorded. Evaluate maintenance separately so necessary financial reconciliation can continue safely.

- A claimed but unstarted item can be reclaimed after its lease expires. An expired `sending` lease becomes `unknown`; it must not be blindly resubmitted.
- SMS `submitted`/`unknown` items with a known provider ID receive bounded status reconciliation. Missing-provider-ID and unresolved email outcomes need operator/provider review; they must not be blindly resent. Under an approved commerce policy, an administrator with recent MFA can explicitly waive the exact held credit for one unknown SMS. The service bears any provider cost, the message remains `unknown`, and late delivery evidence cannot debit its waived reservation. This is a customer charge decision, not proof that the provider did not send the message. Ambiguous payments use the separate bounded reconciliation flow described below.
- A submitted or uncertain SMS retains its credit hold. Confirmed delivery settles the retail quote; terminal failure releases the member hold. Provider charges and actual segments still require cost reconciliation, including failed/undelivered sends. Never release a hold or create a new delivery just because a timeout occurred.
- Reconcile old pending Checkout operations before creating another funding attempt. The API stops retrying a pending operation after 23 hours to avoid exceeding provider idempotency retention. Maintenance performs bounded, resumable provider-session discovery for sufficiently old pending purchases; it never creates another Checkout session during recovery.

## Monitoring and incidents

Set alerts through the authorized host/providers; this repository does not install a monitoring service. Monitor missing cron runs, repeated busy leases, planning lag/expired work, provider errors, unprocessed webhooks, aged unknown/submitted sends, old held credit, pending checkouts, blocked wallets, SMTP/OTP failures, bounce/complaint rates, quota exhaustion, and database connection/lock pressure. Choose thresholds and an on-call owner before launch. `/api/health` is process liveness only. Prefer `GET /api/jobs/readiness` and `pnpm ops:monitor` with the separate read-only monitoring secret for routine checks. The cron-token-protected `GET /api/jobs/status` remains an operator diagnostic for aggregate delivery counts/oldest records, blocked wallets, aged unprocessed webhooks and planner status. Neither endpoint returns recipient identities or verifies external services; do not give the mutation-capable cron secret to a read-only monitoring integration.

Use opaque request/delivery/event IDs and safe error categories for correlation. Never log OTPs, auth cookies, API keys, raw recipient addresses/numbers, private reflections, source preferences, full provider payloads, unsubscribe tokens, or full connection URLs. Host access logs can expose token query strings unless configured to redact them. Configure redaction and log retention outside the app as well.

For an incident, contain the affected outbound/payment capability, preserve non-sensitive evidence and immutable financial records, check authoritative provider results, reconcile one operation at a time, and verify recovery with authorized test destinations. Communicate delays accurately. A rollback does not undo an already-submitted message or accepted payment.

## Refunds, disputes, export, and deletion

Stripe refund/dispute events record durable evidence; external or ambiguous losses restrict the associated wallet. The administrator workspace can request a durable refund of unused credit, cancel an eligible never-submitted or proven-absent request, and resolve incidents using complete authoritative provider evidence. Refund submission runs through maintenance; uncertain outcomes keep their holds. The resolution derives its adjustment and retains a restriction for unrecovered debt or unresolved evidence; it is not an arbitrary balance edit or unconditional unfreeze button. The app does not submit dispute evidence to Stripe. See [financial operations](financial-operations.md) for statuses, ordering, and recovery limits. Never delete or rewrite immutable ledger rows to force a balance. Tax, unused-credit, partial-refund, merchant-funded uncertain-message waivers, failed-delivery charging, and closure terms require an approved policy before commerce activation.

Deletion is blocked while available/reserved funds, blocked financial status, pending checkouts, or unresolved sends remain. An unknown SMS whose exact reservation has been explicitly waived no longer blocks deletion on its own; other obligations still do. Once permitted, the app freezes the profile, pauses/cancels pending work, withdraws consent, records suppression, and requests Supabase identity deletion. If identity deletion fails, `DELETION_PENDING`/`ACCOUNT_DELETING` allows the member to retry or sign out; no completed deletion should be claimed until the provider confirms it.

Deleting the auth identity cascades private profile/preferences, contacts, notes, saved/completion records, consent history, deliveries, and attempts. Financial records remain without the user association; keyed destination suppression remains. Third-party provider records and backups have their own retention. The implemented maintenance job removes expired phone challenges and old rate-limit buckets and redacts eligible terminal delivery payloads according to an explicit approved policy. It does not delete immutable financial evidence, suppression, or webhook deduplication records. No legal retention periods have been approved. Configure the remaining evidence/backup lifecycle with the operator's obligations; see [production operations](production-operations.md).

## Maintenance and preflight limits

Maintain the 24 practices in `packages/content`, preserve stable IDs, review interpretation/source links, and run content/message tests. The implemented [content pipeline](content-pipeline.md) adds complete-inventory import, source permissions, structured AI drafts and human publication. No real corpus or AI account is activated. Use the bounded `pnpm content:manage` commands for reviewed source registration/rights/import; they default to no writes, and applying changes requires the explicit actor and current operator authorization. The [operator guide](operator-guide.md) covers role administration, MFA and review/publish/withdraw. Source permissions and human editorial approval remain essential; model memory is never the source of a reference. Review photo rights and dependency advisories deliberately; use frozen lockfiles and verify upgrades against affected provider contracts.

Use `GET /api/jobs/readiness` with the separate `MONITORING_SECRET` for aggregate migration, configuration, RLS, planner and maintenance checks. `pnpm ops:monitor` performs this bounded check without exposing recipients or credentials. `/api/jobs/status` remains available to cron operators for additional aggregate diagnostics. Neither endpoint verifies real external delivery or payment. Run a test alert and recovery on the selected host before launch.

`pnpm release:preflight` validates supplied configuration and prints missing requirements without secret values. It rejects repeated application-secret values, a non-HTTPS Supabase endpoint, and a non-live Stripe key prefix when live payment mode is selected. A passing result does not prove entropy/key validity, project ownership, matching auth/database projects, SMTP templates, provider approval, callback reachability, cron configuration, database migration/RLS state, restored backups, or legal/commerce readiness. It permits disabled capabilities, so inspect the intended launch scope separately. Review sender identity and trusted edge-header configuration outside the script. Do not interpret `configurationReady` as authorization to deploy.

The 2026-10-24 production and full dependency audits for the website, dashboard and backend, plus the root tooling audit, report no findings after the targeted Next.js 16.4.1 and Zod updates. The earlier braces advisory was withdrawn upstream, not patched by this project. See [dependency review](dependency-review.md) for the official sources and historical results. Keep build/lint jobs isolated and least-privileged and rerun both audit scopes when dependencies or advisories change. A clean audit is not proof of application security.

Follow [release gates](release.md), [testing](testing.md), and [production operations](production-operations.md). Record a tested revision and actual evidence for each environment; never promote mock or local database tests into claims of real payment, hosted recovery or delivery.
