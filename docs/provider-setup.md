# Provider setup and operating boundaries

This is an implementation guide, not evidence that accounts, payments, or deliveries have been activated. The provider tests use injected request mocks and locally generated webhook signatures. No real recipient, card, provider account, DNS record, or purchased number was used by those tests.

## Product and release prerequisites

Accounts and practice emails are free. Canadian SMS is optional prepaid service credit in CAD, with $10, $25 and $50 top-ups. There is no subscription or automatic recharge. The server-controlled rate per SMS segment must be visible before a purchase; a message can consume several segments. Verify applicable taxes and publish approved refund, unused-credit and account-closure terms before enabling payments. Service credit is not a Stripe balance top-up or a general-purpose transferable wallet.

Set your public `SUPPORT_EMAIL`, `OPERATOR_NAME` and `OPERATOR_MAILING_ADDRESS` consistently in both apps. Public pages and member consent display those details. Missing or invalid identity/contact disables new grants, sending and checkout. No original developer contact or placeholder identity is substituted. Supply your own privacy/retention, commerce and consent policies before real use.

## Configuration

Keep every secret below server-side, in deployment secrets or an ignored environment file. Public build flags and URLs contain no secrets. `NEXT_PUBLIC_APP_MODE=preview` preserves the local demonstration; `live` routes to server account features but does not activate the separate delivery/payment flags.

| Setting                                                             | Purpose                                                                                                                |
| ------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `APP_ORIGIN`                                                        | Canonical absolute dashboard origin, HTTPS in deployment; the source of callback URLs, never forwarded request headers |
| `NEXT_PUBLIC_APP_MODE`                                              | `preview` or `live`, kept consistent across both applications                                                          |
| `NEXT_PUBLIC_SITE_URL`, `NEXT_PUBLIC_DASHBOARD_URL`                 | Public website and member origins                                                                                      |
| `OPERATOR_NAME`, `OPERATOR_MAILING_ADDRESS`                         | Real sender identity and postal address; required for live sending                                                     |
| `EMAIL_FROM`                                                        | Verified sender, for example `Jesus in Practice <lessons@your-verified-domain>`; never use the example literally       |
| `RESEND_API_KEY`, `RESEND_WEBHOOK_SECRET`                           | Restricted sending key and webhook signing secret                                                                      |
| `TWILIO_ACCOUNT_SID`, `TWILIO_API_KEY_SID`, `TWILIO_API_KEY_SECRET` | Account and API credentials used for outbound requests                                                                 |
| `TWILIO_AUTH_TOKEN`                                                 | Account auth token used by the SDK to validate callbacks; distinct from API-key secret                                 |
| `TWILIO_VERIFY_SERVICE_SID`, `TWILIO_MESSAGING_SERVICE_SID`         | Separate Verify and lesson messaging services                                                                          |
| `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `STRIPE_LIVE_MODE`    | Mode-matched Stripe API/signing credentials; live mode defaults off                                                    |
| `SMS_SEGMENT_PRICE_CAD_CENTS`                                       | Approved integer CAD price per segment; never derive by rounding a USD provider charge                                 |
| `ENABLE_PAYMENTS`, `COMMERCE_POLICY_APPROVED`                       | Explicit payment gates after setup and terms review                                                                    |
| `ENABLE_EMAIL_DELIVERY`, `ENABLE_SMS_DELIVERY`                      | Explicit channel delivery gates after account/consent/provider verification                                            |

The member UI displays the approved CAD price per SMS segment before consent. A grant carries `consentVersion`, derived from the bundled wording version and the rate shown to that member. The server rejects a stale version with `409 CONSENT_CHANGED`; the UI refreshes and requires another explicit grant. The server stores the wording/rate version and the worker checks it when planning and immediately before submission. Changing price or consent wording therefore requires renewed consent; withdrawals do not require a version. A displayed price is not permission to change an existing grant silently.

The application config is authoritative for operational quotas and additional database, authentication, queue and token secrets. Provider adapters receive validated config and have no `process.env` reads. Their caller deadline is at most 15 seconds. A timeout bounds the wait, not proof that work was cancelled remotely.

## Stripe: CAD credit funding

1. Create the authorised Stripe account and complete its verification. Start with test mode; create separate test/live API and endpoint-signing credentials. Enable card payments for the relevant Checkout configuration.
2. Use hosted Checkout for one-time CAD payments. The server supplies an allowlisted amount, user ID and opaque funding ID; the browser never selects an arbitrary currency, owner or credited amount. Stripe SDK 23 uses `allowed_payment_method_types: ["card"]` to filter enabled methods.
3. Register `APP_ORIGIN/api/webhooks/stripe` with the exact handled events listed below. Receive the raw body and verify its signature before parsing or trusting it. Preserve `livemode` validation and record each event ID durably. Use separate endpoint/signing credentials for test and live modes.
4. The success URL is `/wallet?checkout=complete`; cancellation is `/wallet?checkout=cancelled`. A redirect is not payment proof. Retrieve the Checkout session, match session ID, user, funding ID, mode, currency and exact amount, and credit only a paid payment with a PaymentIntent ID. Deduplicate both event and underlying funding/payment so retries cannot create credit twice.
5. Reuse `sms-funding/<fundingId>` only with the exact same parameters. The SDK allows two network retries for keyed creation and safe reads. After the caller times out, reconcile the original operation; do not create a fresh funding ID to conceal uncertainty. Stripe normally retains idempotency results for at least 24 hours, so local durable records must outlive provider key retention.
6. Before enabling payment, test a successful card, decline, cancelled/expired Checkout, repeated webhook, out-of-order events, wrong amount/owner/currency, provider timeout and the operator refund/reconciliation path using the official sandbox. Then verify an authorised production transaction and refund only with explicit approval for those financial actions. Refunds/disputes require an operational policy; account deletion must not silently discard money or erase audit records.

Subscribe to all eleven event types handled by `apps/dashboard/app/api/webhooks/stripe/route.ts`:

| Purpose                     | Events                                                                                                                                        |
| --------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| Checkout funding and expiry | `checkout.session.completed`, `checkout.session.async_payment_succeeded`, `checkout.session.expired`, `checkout.session.async_payment_failed` |
| Charge refund evidence      | `charge.refunded`                                                                                                                             |
| Refund operation updates    | `refund.created`, `refund.updated`, `refund.failed`                                                                                           |
| Dispute review              | `charge.dispute.created`, `charge.dispute.updated`, `charge.dispute.closed`                                                                   |

Refund events reconcile a matching durable refund operation using authoritative provider state. An unmatched refund or dispute restricts the associated wallet for review; a closed dispute event does not itself authorize an unconditional unfreeze. Charge-refund evidence also enters financial reconciliation. Retain every listed event when configuring the endpoint: completion alone cannot maintain refund/dispute state. The implementation does not depend on a separate `payment_intent.succeeded` subscription. See [financial operations](financial-operations.md) and the [operator guide](operator-guide.md) for the audited refund/resolve/cancellation workflow, recent-MFA requirements, holds and uncertainty rules.

Official references: [fulfilment](https://docs.stripe.com/checkout/fulfillment), [idempotent requests](https://docs.stripe.com/api/idempotent_requests), [webhooks](https://docs.stripe.com/webhooks), [refunds](https://docs.stripe.com/refunds). Stripe's [Top-ups API](https://docs.stripe.com/api/topups) funds a Stripe balance; it is not the member credit ledger.

## Twilio: Canada verification and SMS

Register the business or individual that actually operates your installation. Follow Twilio's current requirements for that operator type; do not invent a business registration number or assume that identity verification approves a sender. Register the selected number with the actual contact details, public website and opt-in evidence, and wait for the applicable provider review. [Twilio registration fields](https://www.twilio.com/docs/messaging/api/tollfree-verification-resource), [registration requirement update](https://www.twilio.com/en-us/changelog/business-registration-numbers-required-for-toll-free-messaging-p)

Use a **Restricted API key in US1**, matching the adapter's default region. Grant only these five runtime permissions, using Twilio's official [Lookup](https://docs-resources.prod.twilio.com/documents/Twilio_Restricted_API_Keys_Permissions_-_Lookup_Permissions.pdf), [Verify](https://docs-resources.prod.twilio.com/documents/Twilio_Restricted_API_Keys_Permissions_-_Verify_Permissions.pdf), and [Messaging](https://docs-resources.prod.twilio.com/documents/Twilio_Restricted_API_Keys_Permissions_-_Messaging_Permissions.pdf) mappings:

| Adapter operation          | Permission                                |
| -------------------------- | ----------------------------------------- |
| Basic Lookup               | `/twilio/lookup/phone-numbers/read`       |
| Start phone verification   | `twilio/verify/verification/create`       |
| Check verification code    | `twilio/verify/verification-check/create` |
| Submit practice SMS        | `twilio/messaging/messages/create`        |
| Fetch known message status | `twilio/messaging/messages/read`          |

Store the key SID/secret separately from `TWILIO_AUTH_TOKEN`. Webhook validation requires the account's **primary Auth Token**; the API-key secret does not replace it. The Auth Token also grants broad REST access, so keep it server-side even when outbound API requests use the restricted key. See [regional key creation](https://www.twilio.com/docs/iam/api-keys/keys-in-console) and [signature validation](https://www.twilio.com/docs/usage/security).

For a read-only setup check, keep `ENABLE_SMS_DELIVERY=false` and `ENABLE_PHONE_VERIFICATION=false`. Perform one [Basic Lookup](https://www.twilio.com/docs/lookup/v2-api) with a [reserved Canadian fictional number](https://www.cnac.ca/other_codes/555/555_line_numbers.htm), without any additional `Fields` packages. A successful response proves authenticated Lookup access even if the synthetic number returns `valid:false`; it does not prove phone ownership or reachability. Confirm that the runtime key denies service/account reads. The separately configured primary Auth Token can fetch the two exact configured services to check account ownership, six-digit Verify codes, and disabled Smart Encoding/MMS conversion, without adding permissions to the runtime key. Bound reads to 15 seconds without retries and retain only aggregate evidence. These checks do not verify SMS submission, Verify code delivery/checks, or provider callback delivery. Retain provider identifiers privately and summarize the actual checks in your installation's [release evidence](release.md).

1. Create the authorised account, API credentials and separate Verify/Messaging services. Set appropriate Verify fraud controls, geographic permissions, request limits and monitoring. Phone proof is granted only for an `approved` check matching the destination. A missing/expired Verify result is never treated as success.
2. Validate an E.164 number and use Lookup's `countryCode=CA` before verification or lesson eligibility. `+1` alone includes the United States and other NANP destinations. Recheck country and proof when a destination changes; possession does not imply consent to recurring lessons.
3. Provision an authorised toll-free sender, complete toll-free verification, and attach it to a Messaging Service. This purchase and approval are external setup tasks, not actions completed by this implementation. Supply real operator information, opt-in evidence, separate privacy/terms URLs and accurate message frequency, support and STOP instructions. Review current requirements directly before submission.
4. Keep Smart Encoding and MMS conversion disabled so the application calculates the same final body that is sent. This implementation assumes SMS through a Canada/US toll-free sender, not RCS/MMS or a mixture of sender types. Enable Advanced Opt-Out and set the inbound webhook to `/api/webhooks/twilio/inbound`. Handle `OptOutType` and error 21610 promptly; do not send another confirmation when Twilio has already replied. START must not silently bypass the application's consent requirements.
5. The adapter supplies `/api/webhooks/twilio/status?deliveryId=<opaque-id>` as each message's status callback. Validate the SDK signature using the configured canonical HTTPS URL, full query and all form fields. Reject unexpected accounts, paths and duplicate fields. Never construct the signed URL from an untrusted Host or forwarded header. Persist/deduplicate callbacks and tolerate out-of-order status events.
6. The adapter disables automatic retries. A transport error or timeout after submission is `unknown`; retain the wallet reservation and reconcile callbacks/provider records. Never blindly resend an unknown SMS. API acceptance/queued/sent is not recipient delivery. A missing callback is not proof of failure or permission to release and resend.
7. Freeze the entire rendered body before reserving credit and submitting it. It contains sender, source/reference, original meaning, example, action, disclaimer, STOP and an operator-information URL. Calculate the quoted charge from its segments and the disclosed CAD rate. Reject an over-cap message rather than truncating its reference or opt-out instructions. A confirmed non-billable rejection can release a reservation; reconcile provider failures, actual segment count and charges before settlement. Do not assume failed/undelivered means the provider charged nothing.
8. Single SMS capacity is 160 GSM-7 septets or 70 UTF-16 units; toll-free multipart capacity is 152 or 66. Extension characters use two septets; emoji may use multiple UTF-16 units. The counter preserves escape pairs and Unicode graphemes at boundaries. Keep provider Smart Encoding and sender type fixed, and reconcile actual provider segment counts; future provider transformations or unsupported grapheme sequences need review. The provider's returned price/currency is operational cost, not automatically the CAD retail charge.
9. Verify a Canadian test destination, approved sender, delivery callback, STOP, HELP, wrong code, expired code, opt-out rejection and provider outage only with authorised recipients. Mock tests and Twilio legacy test credentials do not verify delivery or support all Verify operations. New console accounts may not expose legacy test credentials.

Official references: [Canada guidance](https://www.twilio.com/en-us/guidelines/ca/sms), [toll-free verification](https://www.twilio.com/docs/messaging/api/tollfree-verification-resource), [required verification information](https://help.twilio.com/hc/en-us/articles/13264118705051-Required-Information-for-Toll-Free-Verification), [Verify checks](https://www.twilio.com/docs/verify/api/verification-check), [signature validation](https://www.twilio.com/docs/usage/security), [Advanced Opt-Out](https://www.twilio.com/docs/messaging/tutorials/advanced-opt-out), [message status](https://www.twilio.com/docs/messaging/guides/track-outbound-message-status), [SMS lengths](https://www.twilio.com/docs/glossary/what-sms-character-limit), [maintained SDK](https://github.com/twilio/twilio-node).

## Resend: free practice email

1. Create an authorised Resend account and verify a controlled sending domain or subdomain. Publish the provider's specific DNS records; verify DKIM/SPF and review DMARC before production. Do not invent DNS values or use a Gmail address as a verified domain sender. The support address can remain Reply-To.
2. Use a restricted API key. Configure `/api/webhooks/resend` and its signing secret. Verify raw payload with the SDK's Svix-compatible verifier and the three signature headers. Persist event IDs and apply durable suppression for hard bounces and complaints. The handler also validates recipient addresses from signed bounce/complaint/suppression payloads and records their keyed destination hashes when the original account/delivery row no longer exists, preserving late-event suppression after deletion. A `sent` event means accepted by the sending service; `delivered` means the recipient mail server accepted it, not that it was read.
3. Use a stable `lesson/<deliveryId>` idempotency key and immutable recipient/body for a single delivery. Resend retains keys for 24 hours. Concurrent-key responses and timeouts are uncertain; reconcile before any retry beyond retention. A same-key/different-payload conflict is an application error, not a reason to generate another key.
4. Every recurring practice email includes HTML and plain text, sender postal/contact details, a visible unsubscribe link and RFC 8058 headers. The unsubscribe endpoint must implement unauthenticated token-protected one-click POST and a safe GET confirmation page. Do not let link-prefetch GET requests unexpectedly change consent. Suppress immediately and recheck eligibility before every send.
5. Free user email still incurs service limits and infrastructure cost. Enforce verified destinations, consent, per-account delivery caps, a global daily/monthly provider budget, authentication request throttles and queue backpressure. Failed, bounced and repeated signup traffic must not exhaust the free-email budget. Provider free quotas are not a product promise; check the current account plan before launch.
6. Authentication mail is separate: Supabase Auth and its configured SMTP handle login links/codes. Do not send auth mail through the lesson adapter or require marketing consent to sign in. Configure and test auth redirects and SMTP independently.
7. Use Resend's documented simulated recipients for controlled provider checks before real recipients. Then verify delivery, plain-text rendering, bounce/complaint handling and unsubscribe with authorised addresses. Local tests cover adapter semantics and signatures only.

Official references: [verified domains](https://resend.com/docs/dashboard/domains/introduction), [idempotency](https://resend.com/docs/dashboard/emails/idempotency-keys), [webhook verification](https://resend.com/docs/webhooks/verify-webhooks-requests), [event meanings](https://resend.com/docs/webhooks/event-types), [unsubscribe headers](https://resend.com/docs/dashboard/emails/add-unsubscribe-to-transactional-emails), [quotas](https://resend.com/docs/knowledge-base/account-quotas-and-limits), [test recipients](https://resend.com/docs/knowledge-base/what-email-addresses-to-use-for-testing).

## Scheduling and host integration

Follow [operations](operations.md) for reviewed migrations, the read-only `pnpm db:check` smoke check, canonical origins and callbacks. ## Canadian consent and privacy checks

Free or religious content is not automatically outside CASL; the actual message's purposes determine its treatment. Before launch, obtain advice appropriate to the operator and service. As the conservative implementation baseline, use a separate affirmative opt-in for each lesson channel, record consent wording/version and time, identify the real sender, provide contact details, and offer a simple withdrawal method. Consent is distinct from verification, service terms and payment.

For SMS space constraints, use the permitted clear, prominent, no-cost information-page link with required identity/contact information. Keep contact details and unsubscribe facilities valid for the required period, and honour unsubscribe promptly; the legal maximum is not a reason to delay suppression. Publish actual processors, processing locations, purposes, retention and access/deletion procedures; religious preferences and reflections deserve particular care. Never send reflections to messaging/payment providers.

Official references: [CRTC CASL FAQ](https://crtc.gc.ca/eng/com500/faq500.htm), [positive opt-in guidance](https://crtc.gc.ca/eng/archive/2012/2012-549.htm), [Electronic Commerce Protection Regulations](https://laws-lois.justice.gc.ca/eng/regulations/SOR-2012-36/FullText.html).
