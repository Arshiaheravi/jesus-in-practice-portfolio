# Frontend scope and acceptance journeys

This document preserves the frontend phase's preview scope and acceptance criteria. The project now also implements a separate authenticated live mode; see [backend architecture](backend-handoff.md) and [API contract](backend-api.md) for that mode. Statements below about browser-local data, simulated entry, and absent delivery apply to the default preview, not the live API implementation. No production service is established by either mode's source code. Record executed checks and their actual results separately.

## Product decisions

- Name: Jesus in Practice. Initial audience: people in Canada who want practical scripture reflections, including Christians from different traditions and people who are simply curious.
- Initial collection: Bible, identified as KJV. Book of Mormon and both collections are explicit choices. Source labels and passage links remain visible. A Bible-only preference must not silently include Book of Mormon lessons.
- Each practice connects an exact scripture reference to a plain-language meaning, an illustrative everyday example, one manageable action, and an optional reflection question. Public details, member details, and email previews share this anatomy; SMS uses a shorter attributed version. The shared library contains 24 selected practices, not the whole teaching content of either work. See [content sources](content-sources.md).
- The visual identity uses warm ivory/burgundy, Lora headings, and real photographs related to Jesus, scripture, and prayer. The previous generated illustrations are no longer used. Random preview controls select from bundled examples within the selected sources and topics, avoiding an immediate repeat when alternatives exist. No live AI generation or full-corpus coverage is implied; the future source-grounded workflow is described in [AI content design](ai-content-design.md).
- Delivery experience: email, SMS, or both, with user-selected days, time zone, and a fixed time or same-day delivery window. In this phase these are local preference previews. Saving them does not schedule or send messages.
- Support a sustainable pace. No spiritual scores, competitive streaks, invented outcomes, fabricated testimonials, or financial and health guarantees.
- Preserve the Next.js, React, TypeScript, Tailwind, and pnpm workspace stack. The public website and dashboard remain separate applications sharing the content package.

These are reviewable user journeys, not authorization to build authentication, payment processing, message delivery, or a production database in this phase.

The member route map is `/dashboard`, `/library`, `/library/[slug]`, `/saved`, `/schedule`, `/progress`, `/settings/account`, `/settings/preferences`, `/settings/plans`, `/help`, and `/onboarding`. Entry routes `/signin`, `/signup`, and `/reset-password` explain or demonstrate preview entry rather than authenticating a person. The account screen exports local JSON and offers a confirmed reset. There is no fabricated message-history screen: provider delivery records do not exist in this phase.

## Current local state boundary

The dashboard's `lib/demo-model.ts` and `components/demo-provider.tsx` define the local preview state. The storage key is `jesus-in-practice:preview:v1`; the object has `version: 1`. It contains onboarding completion, source, topic choices, channel, time zone, preview plan, schedule preferences, saved practice IDs, completion records, and notes. It does not define a user identity, authenticated session, verified destination, subscription, payment method, delivery receipt, or consent ledger.

The initial state selects Bible, email, `America/Toronto`, the `explore` preview plan, and an 08:00 fixed-time preference on all days. These are editable preview defaults; they do not subscribe anyone. The supported time-zone options are named IANA zones, including Newfoundland and Saskatchewan examples; this curated list does not represent every Canadian location. Schedule validation accepts one to three distinct fixed times, or a same-day window with an end after its start, plus at least one day. A future real scheduler must separately define daylight-saving behaviour and channel limits.

Notes are limited to 1,500 characters per practice. Local completion history is bounded to the most recent 2,000 stored records. Local data can disappear when browser data is cleared and does not automatically move across devices, browser profiles, ports, or hostnames. In particular, `localhost` and `127.0.0.1` do not share the same storage origin. Browser storage is not encryption or an access-control boundary; use non-sensitive notes for the preview.

Stored state is parsed and validated before reuse. Unsupported or unreadable data can recover to defaults with a recovery notice. If storage cannot be accessed, the provider falls back to memory for the current page session and reports the limitation. Cross-tab storage events update the current local snapshot. None of these mechanisms provides server persistence or account synchronization.

The local clock hook refreshes once per minute. Date calculations use the selected time zone. This is frontend display logic, not evidence of a background job or reminder execution while the app is closed. The practice catalogue is bundled content that changes with a build; it is not fetched from a live scripture or publishing service.

## Verification plan

Use the production builds for the final local review. Record the tested revision, runtime, commands, route coverage, and meaningful limits in the implementation evidence. Do not carry forward the original vendor-template smoke-check results as evidence for these replacement screens.

1. Run repository formatting/lint, type checks, content/model tests, and both production builds. Tests should cover source eligibility, filtering, storage validation, dates, schedule constraints, and activity integrity rather than reproducing component implementation details.
2. Exercise the critical journeys in a real browser at desktop and narrow mobile widths. Inspect visual hierarchy, wrapping, image loading, empty states, and horizontal overflow; check the browser console and failed network requests.
3. Check keyboard-only navigation, visible focus, accessible names, labels and error associations, focus behaviour for menus/dialogs, heading order, contrast, touch targets, and reduced-motion behaviour. Automated accessibility checks complement manual inspection; neither alone establishes complete WCAG conformance.
4. Test persistence after reload, source changes, empty filter results, pause/resume, invalid schedules, long notes, storage denial, malformed stored JSON, an unknown practice ID, export/reset, and multiple tabs when relevant. Use isolated preview data.
5. Inspect metadata, social images, canonical configuration, robots, sitemap, links between the two apps, and indexing defaults. The dashboard stays out of indexing. Public indexing remains disabled until a real domain and launch decision are supplied. Indexing controls are not authentication.
6. Verify that clicking a preview confirmation does not send messages, accept a payment, create an account, or falsely report a remote success. Service-provider and authentication checks remain unavailable until those integrations exist.

## Completion boundary and release gates

A completed frontend means the agreed local journeys work, the visual and accessibility review has been performed, content is internally consistent, and relevant checks pass at the recorded revision. It does not mean the subscription service is production-ready or that the entire product has a guaranteed level of security, accessibility, reliability, or theological correctness.

The project owner must settle the production domain and hosting target, final commercial prices/limits, legal operator identity and contact details, content approval process, target age audience, and messaging/authentication/payment providers before launch. The public legal pages are preview-specific information, not final service policies. No price, legal identity, support channel, certification, or provider relationship should be invented to fill those gaps.

See [backend handoff](backend-handoff.md) for the remaining service work and production verification gates. Deployment of the paid service requires that work and verification through an authorized release process; local preview readiness alone does not satisfy them.
